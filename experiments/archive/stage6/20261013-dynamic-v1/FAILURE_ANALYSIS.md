# Stage 6 失败与恢复分析

## 固定 30 条：两种模式均 28/30

cb2-r03、cb2-r04 的历史 gold 标注 MODERATE，当前结构化输出为 LOW + needs_human_support=true。两种模式都正确转 HUMAN_SUPPORT 并创建工单，只有 risk 标签检查失败；原始评分保留在 evaluation.json。自然案例18/20，受控故障10/10。

Dynamic 在 cb2-k02 首次生成漏写来源标记，触发 CITATION_REQUIRED，使用一次重生成后交付带有效来源的回复。这使正式30条的外部请求从125增加到126、输入 tokens 增加841、输出增加211。任务执行减少主要来自 Context 的条件跳过，当前实验没有展示模型请求费用下降。

cb2-v05 指定 citation_missing 故障两次都被确定性校验拒绝，按原 reference 进入 SAFE_FALLBACK。cb2-p02 的超时仍只注入到 ResponseAgent 第一次调用，其他 Agent 使用正常 deadline；风险工单保持可查询。审核拒绝、异常、候选错配与调用失败的其他控制用例继续通过。

## 边界 12 条：10/12 → 12/12

| 案例 | Sequential 实际问题 | Dynamic 行为 |
|---|---|---|
| cb5-k05 | 词面检索命中无关校园资料，模型按未命中表述回复却带不合格引用；重试后兜底，retrieval_status 与有效知识答复检查失败 | 仲裁去掉无关证据，Context 转 NO_HIT，生成明确“没有找到”回复，ACCEPTED、无引用 |
| cb5-k06 | 用户自带伪造 `[source:...]` 被生成文本复述，来源白名单拒绝，重试仍不通过而兜底 | 只在 Response 输入视图把伪造标识当普通数据；保留原始消息，使用本轮无障碍支持与资助来源，ACCEPTED |

以上两个修复对应 Dynamic 的预先固定策略。正式运行结束后未更换 Prompt、重试挑选结果或调整测试数据。来源的白名单、revision、内容 Hash 与候选审批 Hash 检查继续生效。

## 编排与可靠性

所有成对运行中，计划 DAG、依赖状态、任务区间、终态和交付绑定检查100%通过。Dynamic 固定30的35个总轮次中30轮分析区间真实重叠，历史指代轮次保留串行依赖；边界12的13轮均可并行。

模型只通过统一端口调用，分析输出由协调器合并。模型 call_id 是任务局部变量，usage 与输出校验不依赖完成顺序。新增测试覆盖反向完成、坏格式、单角色超时、取消与预算耗尽；已经完成的高风险结果在另一角色被取消时仍提交工单。
